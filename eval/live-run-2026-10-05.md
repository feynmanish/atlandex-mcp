Checks per question (unchanged from the previous report): (T) right tools in a sensible order, (S) short terms
passed to `find_videos`, (L) no loops (same tool + same arguments more than twice), (C) every claim cites a
`youtube_url`, copied whole: with its `&t=...s` when the passage has a `start_sec`, and with no timestamp when
`start_sec` is null, (U) no `search_video` retries on unsearchable videos. C was checked by comparing every
YouTube URL in the answer, character for character, with the URLs the tools returned.

Two things the score does not say:

- **The model still does not copy `citation` verbatim.** Every URL in every answer was exactly one the tools
  returned (no bare link for a timestamped passage, no invented timestamp), which is what C measures and what
  failed before. But 8 of the 10 Sonnet answers rewrote at least one link label: dropped the title
  (`[9:21](...)`), shortened it, or wrote `[same talk, 6:30](...)`. Only Q2 and Q9 are verbatim copies. Haiku
  rewrote labels in Q2 (a quoted sentence as the label) and Q10. So the instruction to copy the whole link was
  followed for the part that matters (the URL) and ignored for the label. The failures are gone because the
  URL is now sitting in the output ready to copy, not because the model obeys "copy verbatim".
- **C is about links, not about whether the passage supports the sentence.** Sonnet Q1 completes a quote with
  a bracketed "[is simpler than expected]" that the passage does not contain (it breaks off at "It turns out
  intelligence"), and attributes the "huge surprise" to scaling when the passage is about LLMs running on tiny
  hardware. The summary paragraphs at the end of Q1 and Q3 carry no links (same treatment as the uncited
  bullets in Q2 in the previous report).

## Timing of cited links

This part measures server logic (`start_sec` against the captions), which no wording round touched.
Checked against local captions (youtube-transcript-api in a throwaway venv, fetched fine) for the 25
`search_video` passages returned in the Sonnet round-1 runs for Q4-Q8 (some repeat across calls), comparing
`start_sec` with the cue where the passage's opening words are spoken. The lead-in is 30 s as intended: 24.0
to 31.0 s for 22 passages (the low end where the opening words sit a few seconds into a cue), and
`start_sec` is clamped to 0 for 3 passages within the first 30 s of the video (cues at 3.0, 4.2 and 13.1 s).
Same for `locate_quote`: "put CUDA on GeForce" cue 390.0 s, link 360.

## Fixes made (1-6 are text only in `src/atlandex_mcp/server.py`; 7 changes the output)

1. `find_videos` description and zero-match hint: matching is punctuation-exact ("retrieval-augmented
   generation" 0 hits, "retrieval augmented generation" 3; "self-supervised learning" 2, unhyphenated 0), so
   retry once with hyphens added or removed. The old hint example `'RAG'` matched nothing. (Committed earlier.)
2. Server instructions, round 1: use the tools for "what do people/experts say" questions and YouTube links
   instead of answering from memory; for unsearchable videos say the text cannot be read and cite the chapter
   link from `find_videos`. Fixed Q3 and Q9, not Q1 and Q2.
3. Server instructions, round 2: call `find_videos` first, before answering any AI, tech, business or science
   question about a topic, company or person; if nothing matches, answer normally and say so. Fixed Q1, Q2.
4. `locate_quote` description: it returns only a time, a hit can be approximate, use it only for words already
   known from a passage or the user, never to guess what a speaker said. Fixed Q9.
5. Haiku round: instructions say to copy the `youtube_url` whole, including `&t=...s`, and to say what the
   passages do not cover; the `locate_quote` phrase parameter says "copied as spoken, not keywords or a topic".
   Fixed Haiku Q2 and Q9, not Q10.
6. Last round (commit `14380d9`): instructions and `search_video` description say a passage with a
   `start_sec` always gets its timestamped link and only a null `start_sec` gets the plain link. It did not
   fix Q1 or Q3 (see above).
7. Commit `fd4d74c`: a `citation` field on every `Passage`, `VideoHit` and `Moment` (`citation()` in
   `youtube.py`), a ready-made markdown link built from the same values as `youtube_url`; instructions and the
   `search_video` description say to copy it verbatim and to cite each passage a sentence draws on, and the
   older start_sec link rules were removed as redundant. Fixed Q1 and Q3 at the URL level (see the top).

## Found but not fixable in this repo

`locate_quote` has false positives. For vIRiUUtSggM it returned `found:true` (3851 s) for "purple elephants
dancing on the moon", and `found:true` for phrases that are not in the captions at all ("I am a skeptic",
"Gartner hype cycle", "peak of inflated expectations"). The backend seek accepts any 45-second window that
contains two of the query's words, including words like "on" and "the". The server accepts any `match_source`
it treats as located, and the backend reports non-matches as "transcript" too, so the server cannot tell them
apart. The same phrase for aircAruvnKk answered `found:false` once and `found:true` (598 s) twice later. The
real fix is on the backend: `snippet-seek` should return a match quality or report no match. That is outside
this repo, so it is only mitigated here by the description text above, and listed under Known limits in the
README.
